## 1. 권장 엔진: Unreal Engine 5 (5.4+)

### 1.1 선정 근거
| 요구사항 | UE5 적합성 |
|----------|-----------|

## 2. 프로토타입 범위

### 2.0 M0 그레이박스 소환 프로토타입 — 최우선 과제 (R4 판정)
- **R4 판정 명기**: "그레이박스 소환 프로토타입을 M0 최우선 과제로 명기.
  §1.2 '검의 소재' 룰이 검증 대상의 핵심이다."
- 범위: 큐브 지형 + 캡슐 적 위에서 **응검/환검/허공섬/검침/검침 도약/유전**의
  소재 전이 6종과 신검 분리 보상(도력 가속·환술 강화)만 구현. 아트 제로.
- 검증 질문: ① "검을 어디에 둘까"라는 고민이 교전마다 실제로 발생하는가
  ② 검이 손에 없는 시간이 공포(재미)인가 답답함(스트레스)인가
  ③ 응검 체감 지연 0f(03 문서 §4.3)가 기술적으로 성립하는가.
- 실패 기준 선언: ①이 성립하지 않으면 분리 보상 수치가 아니라 **적 디자인**
  (검이 없는 백연을 노리는 습격형)부터 수정한다 — 수치 튜닝 전에 압력 설계.

### 2.1 버티컬 슬라이스(VS) 목표 선언 — 7지역 기준 재정의 (C-03)
"**구름뫼(지역 3) 대숲~산정 30분 분량**: 장승 세이브 2곳 + 신편 성소 1곳 →
대숲 순환 구간(분기 2개) → 정예 조우 3종 → 미니보스 '장승 먹은 것' → 보스
'산군' 1페이즈"를 최종 품질의 80%로 구현. 재미 검증의 최소 단위는 **검침 도약이
열린 상태의 전투**(필수 신편 1·2 회수 후 시점)이므로 지역 1~2가 아닌 구름뫼를
슬라이스로 선정한다. ※ 구판 '2장 중반, 보스 창귀 대장' 정의는 6장 구조와 함께
폐기(C-03) — 창귀 모티프는 산군전(범아귀 기믹 이식 없이 창귀 설화 원형만,
C-09)으로 승계.

## 3. 시스템 아키텍처 개요

### 3.1 검의 소재(所在) 상태 관리 — 아키텍처 1급 시민 (D-2·§1.2 이행)

사인참사검은 **월드에 단 하나 존재하는 독립 액터** `ASacredSword`이며, 그 소재는
전역 서브시스템 `SwordStateSubsystem`이 **단일 창구**로 관리한다. 검의 위치·
소유권에 관한 모든 질의와 전이는 이 서브시스템을 경유한다(직접 어태치/디태치
금지 컨벤션).

```
                    ┌────────────── SwordStateSubsystem ──────────────┐
                    │  상태: ESwordLocus { Hand, Void, Planted, Flight } │
                    │  불변식: 항상 정확히 1개 상태. 전이는 원자적.        │
                    └──────────────────────────────────────────────────┘
   [Hand 손] ──환검──▶ [Void 허공] ──허공섬/유전──▶ [Flight 비행] ──완료──▶ [Void]
      │  ▲                │  ▲                          │(피격·차단)
    검침 │응검           검침 │응검(원거리: 소환 연출)      ▼
      ▼  │                ▼  │                    [Planted 꽂힘] (보스 '검침 카운터'
   [Planted 꽂힘] ◀───────┘  └──── 검침 도약(신행) ──── 시 소유권 임시 이전 상태 포함)
```

- **불변식(Invariant)**: ① 검은 항상 정확히 한 상태 ② 전이는
  `RequestTransition(from, to, reason)` 원자 연산으로만 ③ 실패한 전이는 상태를
  바꾸지 않는다(예: 도달 불가 지점 허공섬 → Void 유지 + 실패 UX).
  런타임 assert + 텔레메트리로 불변식 위반을 0건 유지(크래시보다 우선 감지).
- **소유권(Ownership)**: 기본 소유자는 백연. 보스 '검침 카운터'류 기믹은
  `Planted(Owner=Boss)` 서브상태로 표현 — 상태 종류를 늘리지 않고 소유자
  필드만 전이(전투 파트 기믹 요구 대응).
- **모든 소비자는 구독자**: HUD 검의 소재 표시(03 문서 §2.2), 캐릭터 소매 인장
  발광, 진(陣) 지속 판정(`07` §1 — Planted 해제 시 진 소멸), 검침 도약 유효성,
  애니메이션 어태치 이벤트, AI("검 없는 백연"을 노리는 습격형의 판단 입력)가
  전부 이 서브시스템의 델리게이트를 구독한다.
- **세이브 연동**: 세이브 시점(장승·구역 경계)에는 검을 Hand 또는 Void로 정규화
  (Planted/Flight 중 세이브 금지 — 전투 중 세이브 금지 룰과 자연 일치).
- 구판 `SwordAnchorSubsystem`(앵커 최대 4)은 폐기. 검침 앵커는 **항상 최대 1**
  이므로 앵커 배열이 아니라 단일 옵셔널 필드다. 앵커 유효성(수명 20초, 거리,
  내비 도달성) 질의 창구는 동일하게 본 서브시스템으로 단일화.

### 3.2 전투 상태머신 (플레이어)
계층형 상태머신(HSM) + 상태별 캔슬 태그. 상태 전이는 전부 데이터(캔슬 테이블)
주도 — 기획자가 코드 수정 없이 창 조정 가능해야 함.

```
[Locomotion] ── 공격입력 ──▶ [MeleeString(n)]   ※ 진입 전제: SwordLocus == Hand
     │                          │  (아니면 응검 선행 상태 자동 삽입, 0f 체감 원칙)
     │                          │  cancel: [dodge, mystic, sword_art] + 창(f) 정의
     ├─▶ [Dodge] ◀── 캔슬 창 내 회피입력 (i-frame 2~10f)
     │      └─ 저스트 판정 → [HollinStep] (시간감속·잔상 스폰)
     ├─▶ [Parry] ─ 성공 → [Riposte] / 실패 → [ParryRecover(24f)]
     ├─▶ [MysticCast] ─ 투사체형은 발사 후 조기 탈출 가능
     ├─▶ [SwordArt] (허공섬/검침/유전/진 전개 서브스테이트
     │               — 각 스테이트가 SwordStateSubsystem에 전이 요청)
     ├─▶ [Purify(참사)] (사기 노출 대상 근접 시에만 진입. 인간형은 [Subdue(제압)] 분기)
     └─▶ [HitReact] / [Exhausted] / [Dead]
```
- **캔슬 테이블 스키마(초안)**: `{state, from_frame, to_frame, allowed:[...],
  buffer_consume:bool}` — DataTable 1행 = 1창.
- 입력 버퍼(12f, 큐 1)는 상태머신 바깥의 InputBroker가 소유 — 상태는 버퍼를
  소비만 한다(선입력 버그 격리).

### 3.3 도술 시전 파이프라인
```
입력(퀵슬롯/인장휠)
 → [1] CastRequest 생성 {spell_id, aim, caster_state}
 → [2] 검증 게이트: 도력(여우구슬) 잔량 → 상태 캔슬 가능? → SwordLocus 전제 충족?
        (예: 허공섬은 Void, 진 전개는 Planted) → 매혹 면역 대상?
 → [3] 비용 선지불 (실패 환불 규칙: 소환 위치 보정 실패 시 50%)
 → [4] 태그 조합 판정: 최근 2초 내 활성 SpellTag와 조합표 조회
        → 히트 시 spell_id를 강화판으로 치환 (예: 호화탄 + Void 상태 검 = 점화 인챈트)
 → [5] 실행: GAS Ability 활성화 (몽타주 + Niagara + 판정 스폰
        + SwordStateSubsystem 전이 커밋)
 → [6] 사후 처리: 누진 비용 카운터(+25%/연속), 도술서 발견 기록, 텔레메트리
```
- **조합표는 코드가 아닌 데이터**: `CombineTable {tagA, tagB, window_s,
  result_spell, discovered:bool}` — 신규 조합 추가가 밸런스 작업 수준이 되도록.
- 신검 분리 보상(수치 정본: 02 문서 §2.3 표 — N-03 단일 소스)은 SwordLocus가
  Planted/Flight인 동안 활성되는 상시 GameplayEffect로 구현(Void는 '준분리' —
  별도 경량 태그) — 개별 스킬이 아니라 상태가 버프의 원천.

### 3.4 적 AI·조우 구조
- 잡몹: BT + 그룹 토큰 시스템(동시 공격권 토큰 2~3개 — 포위하되 다구리 금지).
  습격형은 SwordLocus 구독(§3.1) — 검이 손을 떠난 순간 공격 가중치 상승
  (분리 리스크를 AI가 만든다, M0 검증 항목).
- 매혹 상태: AI 팀ID 임시 스왑 + 행동 서브트리 교체(별도 '매혹 AI'를 만들지 않고
  적대 대상만 반전). 회유(`07` §3)는 매혹의 상위 경로 — 스왑 후 문답 시퀀스 성공
  시 영구 중립화 플래그.
- 보스: StateTree로 페이즈(70%/35%) + 패턴 셀렉터(가중치 + 최근 사용 패턴 감쇠).
  '기세 되받기'·'검침 카운터'는 글로벌 인터럽트 레이어.
- 조우 스포너: 디자이너용 EncounterAsset {아키타입 조합, 접두어, 토큰 수, 등장
  연출} — 레벨에 데이터로 배치.

## 4. 팀 요구 툴 (테크니컬 디자인 산출물)
1. **캔슬 창 시각화 툴**: 몽타주 타임라인 위에 캔슬 테이블을 오버레이 표시/편집.

2. **검의 소재 디버거**: SwordLocus 전이 이력 타임라인 + 불변식 위반 알람 +
   상태 강제 전이 치트 (§3.1 전용 QA 툴, M0 산출물).
3. **전투 리플레이·프레임 스텝**: 판정 박스·i-frame·버퍼 상태를 프레임 단위 재생.
4. **밸런스 시트 파이프라인**: 구글시트 → CSV → DataTable 원클릭 임포트 + 값
   범위 검증(04 문서 공식의 상수 자동 반영).
5. **조우 튜닝 모드**: 인게임 콘솔에서 EncounterAsset 핫스왑 + 즉시 리트라이.

### 6.2 협업 워크플로
- 브랜치: trunk 기반 + 기능 브랜치 짧게(3일 상한). 바이너리 에셋은 Perforce
  스트림, 코드/데이터는 Git — M0에서 이중화 여부 최종 결정(팀 익숙도 조사 후).
- 전투 수치 변경은 코드 리뷰가 아니라 **시트 diff 리뷰**로 처리(§4-4 파이프라인
  전제) — 밸런스 디자이너가 엔지니어 없이 하루 3회 이상 이터레이션 가능해야
  한다는 것이 조직적 요구사항.
- 주간 '검증 빌드' 자동 패키징(CI): 입력 지연 측정, 60fps 벤치 씬, 세이브
  마이그레이션 테스트, **SwordLocus 불변식 스모크 테스트**(1,000회 랜덤 전이
  퍼징) 포함.
- 외주 2D 애니(R2): 납품 포맷·프레임레이트·알파 규격을 M2 계약서에 고정,
  수신 검수 체크리스트를 테크니컬 디자인이 관리.

### 6.3 애니메이션 파이프라인 요구
- 검의 소환-소멸이 모든 공격 모션에 얽히므로, 검 메시는 캐릭터에 소켓 부착이
  아니라 **독립 액터 + 어태치 이벤트 노티파이**로 관리 — 손에 쥔 검도 '가장
  가까운 응검 상태'일 뿐이라는 필러 1 원칙의 기술적 구현. 어태치/디태치는
  반드시 SwordStateSubsystem 전이의 결과로만 발생(§3.1 단일 창구).
- 몽타주 노티파이 표준 세트: `HitWindow`, `CancelWindow`, `SwordLocusCommit`
  (구 `SummonSocket` 대체 — 전이 커밋 시점 명시), `VFX_Ink`(수묵 잔향),
  `SFX_Steel` — 신규 노티파이 추가는 테크니컬 디자이너 승인 필수.
